# Perix Sentinel — Collector Revival SDD

> Software Design Document · v0.1
> 목적: **DB 0건 상태인 컬렉터 5개를 다시 데이터가 흐르게 만든다.**
> 선행 조건: P1(http/datetime 공통화) 완료. 후속: Tier1 보강(arXiv·HN)은 이 SDD 완료 후.

---

## 0. 한 줄 요약

5개를 "전부 고장 난 스크래퍼"로 가정하고 수리하지 않는다. **먼저 각자가 왜 0건인지 분류(진단)하고**, 분류에 따라 다른 처방을 적용한다. 실제로 GitHub은 지금 멀쩡히 동작하므로(아래 §3), "수리"가 아니라 "실행"만 필요한 케이스가 섞여 있다.

---

## 1. 목표 (Goals)

1. 대상 컬렉터 5개가 **각각 1건 이상 실제 DB row를 생성**하도록 복구
2. 복구 방식을 **실패 모드별로 분기** (구조 변경 / JS 렌더링 / API 변경 / 미실행)
3. 복구된 live 컬렉터에 한해 **골든 fixture 테스트 1개씩** 추가 (P0 규칙: live만 박제)

## 2. 비목표 (Non-Goals)

- 새 소스 추가 (arXiv·HN) — 이 SDD 완료 **후** 별도 작업
- P2 BaseHtmlCollector 추출 — 부활로 "진짜 공통 패턴"이 확정된 뒤에
- 스코어링 재보정 / LLM 요약 / 스케줄러
- headless 브라우저 상시 도입 (JS 렌더링 대응은 §6의 우선순위에 따라 최후 수단)

---

## 3. 핵심 통찰: "0건 ≠ 고장"

라이브 점검 결과(GitHub, 허용 도메인):

```
HTTP 200 | 654KB | article.Box-row 매치 18개 | 첫 repo 정상 파싱
```

→ **GitHub 컬렉터는 코드 수정 없이 동작한다.** 0건이었던 이유는 스크래퍼 결함이 아니라 **수집 파이프라인에서 실행되지 않았기 때문(미실행, F1)**일 가능성이 높다.

**함의**: 5개를 일괄로 "수리"하면 멀쩡한 코드를 헛되이 뜯게 된다. 반드시 **진단으로 F1(미실행)을 먼저 걸러내야** 한다.

---

## 4. 실패 모드 분류 (Failure Taxonomy)

| ID | 실패 모드 | 증상 | 대표 후보 |
|---|---|---|---|
| **F1** | 미실행 | 단독 실행 시 정상적으로 >0건 반환 | **GitHub (확인됨)** |
| **F2** | HTTP 차단/오류 | 비-200(403/429), 타임아웃, 리다이렉트 루프 | (미상) |
| **F3** | 구조 변경 | 200 OK인데 셀렉터/정규식 매치 0 → "structure may have changed" 경고 | DeepMind, Meta |
| **F4** | JS 렌더링 | 200 OK지만 초기 HTML이 셸, 콘텐츠는 JS로 주입 | DeepMind, Meta(가능성) |
| **F5** | API 계약 변경 | 200인데 JSON 형태/키가 기대와 다름 | HuggingFace |

> Mistral은 이미 Next.js의 `__next_f` 임베디드 JSON을 파싱하는 방식이라, 실패한다면 F4가 아니라 **그 임베디드 구조의 변경(F3 변종)**일 확률이 높다.

---

## 5. 진단 하니스 (Diagnosis First)

수리 전에 **각 컬렉터를 단독 실행해 분류 데이터를 수집**한다. 사이트 접근이 되는 로컬/운영 환경에서 1회 실행.

각 컬렉터에 대해 수집할 신호:

```
- http_status        (F2 판별)
- response_bytes     (셸 페이지면 작음 → F4 단서)
- item_count         (>0 이면 F1)
- warning_fired      ("structure may have changed" → F3)
- exception          (F2)
- raw_head_snippet   (HTML 앞부분 — SPA 셸인지 육안 확인, F4)
- (API의 경우) json_top_level_keys  (F5)
```

분류 규칙:

```
item_count > 0                         → F1 (미실행: 파이프라인 wiring만 손보면 끝)
exception / status != 200              → F2 (헤더·레이트·차단 대응)
status 200 & item_count == 0 & 경고    → F3 (셀렉터 재도출) 또는 F4 (셸 여부 확인)
JSON 키 불일치                          → F5 (API 재매핑)
```

> 산출물: 5×7 진단 표 한 장. 이게 §6 처방의 입력이 된다. (별도 진단 스크립트는 이 SDD의 첨부로 제공 가능)

---

## 6. 분류별 처방 결정 트리

**MVP 원칙: 스크래핑보다 공식 RSS/API가 있으면 무조건 그쪽.** (스크래핑은 깨지기 쉬워 유지비가 큼)

- **F1 (미실행)** → 컬렉터 레지스트리/실행 루프에 포함되었는지만 확인. **코드 수정 0**, 가장 싼 부활.
- **F2 (차단)** → User-Agent 현실화, 레이트리밋·백오프(P1 async_client에 이미 재시도 있음), 그래도 막히면 → 공식 피드/API 대안 탐색 → 없으면 보류.
- **F3 (구조 변경)** → 현재 HTML에서 셀렉터 재도출. **단, 재도출 전에 "이 사이트에 공식 RSS/feed가 있는가?"를 먼저 확인** (있으면 스크래퍼를 피드로 교체가 정답).
- **F4 (JS 렌더링)** → 우선순위: ① 페이지 내 임베디드 JSON 탐색(Mistral의 `__next_f` 패턴 재사용) → ② 공식 API/RSS → ③ (최후) headless. **MVP에서는 ①②까지만, headless는 부채로 미룸.**
- **F5 (API 변경)** → 현재 응답 형태로 매핑 갱신. HF는 `recentlyTrending[].repoData` 가정이 깨졌을 수 있으니 top-level 키부터 재확인.

## 7. 컬렉터별 가설 (코드 기반 사전 예측)

진단 전 가설이며, §5 결과로 확정/기각한다.

| 컬렉터 | 타입 | 현재 셀렉터/방식 | 예상 실패 모드 | 1차 처방 가설 |
|---|---|---|---|---|
| **GitHub** | HTML | `article.Box-row` | **F1 (확인)** | 실행 루프 포함만 |
| **DeepMind** | HTML | `a.card__overlay-link` (매우 특정 클래스) | F3 또는 F4 | 공식 RSS 확인 → 없으면 셀렉터 재도출 |
| **Meta** | HTML | blog href 정규식 + 4단계 부모 휴리스틱 (가장 취약) | F3/F4 | 임베디드 JSON 탐색 우선 |
| **Mistral** | HTML→JSON | Next.js `__next_f` 추출 | F3 변종 (임베디드 구조 변경) | JSON 추출 로직 갱신 |
| **HuggingFace** | API | `?type=model` → `recentlyTrending[].repoData` | F5 | top-level 키 재확인 후 매핑 |

> DeepMind/Meta는 SPA일 확률이 높아 **F4가 나오면 공식 피드 우선**. 두 곳 다 깨지기 쉬운 스크래퍼이므로, 피드가 있으면 그것으로 갈아타는 게 장기적으로 가장 싸다.

## 8. 작업 계획 (Phased)

각 단계 독립 커밋. 브랜치: `fix/collector-revival`.

| Phase | 내용 | 비고 |
|---|---|---|
| **D0** | 진단 하니스 실행 → 5×7 분류 표 작성 | 수리 전 필수 |
| **D1** | F1 처리 (GitHub 등) — 실행 루프 포함 확인 | 코드 0~최소 |
| **D2** | F5 처리 (HuggingFace) — API 매핑 갱신 | JSON이라 빠름 |
| **D3** | F3 처리 (Mistral·DeepMind·Meta 중 해당) — 셀렉터/임베디드 JSON 재도출 | 사이트당 격리 |
| **D4** | F4로 판명된 곳 — 임베디드 JSON/공식 피드로 전환, 불가 시 부채 등록 | headless 보류 |
| **D5** | 부활한 live 컬렉터마다 골든 fixture 테스트 1개 | P0 규칙 준수 |

> 우선순위 = 싼 것부터(F1 → F5 → F3 → F4). 빠른 승리로 데이터가 먼저 흐르게 한다.

---

## 9. 완료 정의 (DoD)

- [ ] 진단 표(5개 × 실패모드) 작성 완료
- [ ] 대상 컬렉터가 각각 단독 실행 시 **≥1건** 반환 (F4로 보류된 건 부채로 명시)
- [ ] `POST /collect` 1회로 **2개 소스 → 4개 이상**으로 실가동 확대
- [ ] 부활한 live 컬렉터마다 골든 fixture 테스트 그린
- [ ] 스크래퍼 대신 공식 RSS/API로 전환한 경우, 그 결정 근거를 PROGRESS에 기록

---

## 10. 리스크 & 완화

- **JS 렌더링(F4)에 시간 빨림** → MVP에서는 headless 금지. 임베디드 JSON/공식 피드까지만 시도하고, 안 되면 **즉시 부채 등록 후 다음으로**. 한 소스에 막혀 전체가 지연되지 않게.
- **재차단(F2 재발)** → 한 사이트라도 차단되면 P1 격리(컬렉터별 try/except)가 있는지 확인. 없으면 그 격리부터.
- **골든 fixture 조기 박제** → 부활이 "임시 동작"이면 박제 보류. 안정 확인 후 fixture.

## 11. 다음 연결 (이 SDD 이후)

부활 완료 → **Tier1 보강**:
- arXiv (공식 API) — AI 연구 1차 발생원
- Hacker News (Firebase 공식 API) — 인디/오픈소스 1차 신호

둘 다 **API 기반이라 스크래퍼 리스크 없음** → 부활에서 검증된 컬렉터 구조 위에 안정적으로 추가.
이후 소스가 충분해지면 → **스코어링 재보정(17%→5%)** 단계로.
